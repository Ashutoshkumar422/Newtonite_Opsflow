# Engineering decisions

---

## 1. A modular monolith on PostgreSQL, plus one separate worker process

**Context.** One day of build time, a reviewer who must run it locally, and a problem whose hard
parts are *consistency* between tightly related records (an item, its audit trail, its assignee's
team membership). Scale target: thousands of users, tens of thousands of active items.


**Why.** Every critical invariant here (claim exactly once, change ⇔ audit row, assignee ∈ team)
spans several tables and is trivially atomic inside one PostgreSQL transaction. Splitting services
would turn each into a distributed-consistency problem (sagas, compensations) with no scale
benefit at this size: a single well-indexed Postgres serves this workload comfortably (benchmarks
in the final report: ~10–35 ms per request on 50 k items). The worker is separate because
notification delivery has a different failure profile and must never block or fail a user action.

**Trade-offs / limitations.** One deployable means one blast radius and one scaling unit (but API
replicas are stateless and scale horizontally; the worker scales with `SKIP LOCKED`). Module
boundaries are enforced by convention, not by the build.

---

## 2. Invariants live in the database, not only in Python

**Context.** "Important actions should not silently disappear", and the data must stay correct
under concurrency and under bugs in future code paths.


Modelling choices that follow: priority is a `smallint` rank so `ORDER BY priority` is correct and
indexable; audit rows store a `jsonb` `{field: {from, to}}` diff so one table covers every action;
comments are a separate, editable table because discussion is user content, while the activity log
is evidence (see `docs/DATABASE_DESIGN.md`). Items are never hard-deleted — cancellation is a
workflow state — so foreign keys are `ON DELETE RESTRICT`.

**Trade-offs.** Rules exist in two places (service messages for users, constraints as a backstop),
and the schema is hand-written SQL rather than ORM-autogenerated. Tests assert both layers
(`test_database_rejects_owned_state_without_assignee`, `test_audit_log_is_append_only_in_the_database`).

---

## 3. Authorization: small role model, one policy module, resource-level checks everywhere

**Context.** Multiple teams; users in several teams with different responsibilities; the brief
requires authorization enforced by the system, not by hidden buttons.

Two deliberate details: resources in teams you do not belong to return **404, not 403**, so item
ids do not reveal existence across teams; and each item response carries a `permissions` object
computed by the same policy functions, which the UI uses to decide what to show — the server
still rejects anything the UI might send anyway.

**Trade-offs / limitations.** Roles are fixed in code; a new role means code changes. Admins act
as managers everywhere (no separation of duties — e.g. a manager can approve their own
resolution). The user directory (`GET /users`) is visible to all employees.

---

## 4. Concurrent updates: compare-and-set for claims, row lock + optimistic version for edits

**Context.** Two people claim the same item; someone edits an item another person just changed;
several updates arrive within milliseconds.

**Trade-offs.** Clients must carry versions; a no-op edit does not bump the version (by design,
to avoid audit noise). Hot items serialize writers on one row lock — fine for human-speed
collaboration, not for high-frequency machine updates.

---

## 5. Idempotency keys stored in the same transaction as the side effect

**Context.** "A user repeating an action because they are unsure whether the first request
succeeded" — and the SPA itself retries on network failure.

The SPA generates one key per user action (per form for creation) and `lib/api.ts` retries network
failures with that same key; requests without a key are never retried automatically.

**Trade-offs.** Replays return the original response even if the item has changed since (the
standard semantics). Keys are purged lazily and hourly by the worker; storage grows with write
volume for 24 h.

---

## 6. Synchronous core, asynchronous notifications via a transactional outbox — and what I did not build

**Context.** The brief invites async processing for secondary work and asks what happens when it
fails, runs twice, or is delayed.

**Trade-offs.** Polling the outbox adds up to ~2 s notification latency; the outbox table needs
periodic archiving at high volume (processed rows are kept for auditability today).

---

## 7. Identity: revocable DB sessions, PostgreSQL-backed throttling, OIDC single sign-on

**Context.** The first iteration used stateless JWTs and had no user administration, rate limiting
or SSO. For an internal tool that holds payment and compliance work, three gaps matter: a stolen or
departing employee's token stays valid until it expires; passwords can be guessed without limit;
and companies want employees to sign in with the corporate identity provider.

**Trade-offs / limitations.** One extra indexed query per request (sub-millisecond; the benchmark
still shows ~10–35 ms end to end). Fixed windows allow a burst at a window boundary (a sliding
window or token bucket would smooth it). No MFA of our own — the intended path is to require it
at the identity provider. No SCIM provisioning or IdP-group-to-team mapping yet. The bundled
development IdP authenticates nobody and exists only for demos and tests.
